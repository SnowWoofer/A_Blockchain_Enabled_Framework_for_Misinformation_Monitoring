FULL SYSTEM TEST CHECKLIST
==========================
For the current named Fabric deployment, full feed pipeline and official Caliper.
Prepared: 18 October 2026. Run commands from the project root in Linux/WSL.

This is a checklist to run manually, not a shell script. Tick each [ ] after
checking its expected result. Creating this file does not execute these tests.

WHAT COUNTS AS A NORMAL FUNCTIONAL PASS?
  Complete sections 1-8 for your selected deployment. Section 9 covers additional
  configurations; section 10 is optional AI evaluation; section 11 deliberately
  changes synthetic content/credentials in a separate disposable deployment.
  Section 12 is the evidence/reproducibility checklist.

Before starting:
  - Use one benchmark at a time. Stop Explorer during timed measurements.
  - A successful command normally exits with code 0. Run echo $? immediately
    afterward if unsure. The deliberate rejection test explicitly expects 1.
  - Startup's smoke check, feed tests and Caliper writes append test records.
    They are not read-only. Repeating them grows the ledger.
  - Use the current feed command: benchmarks/pipeline.py. The older command
    called benchmarks/feed_samples.py is a different, direct-service workflow.
  - Keep the required scripts if you are following this complete checklist.
    Some optional research/check tools were listed as removable for normal use.
  - Do not delete runtime folders, credentials or Docker volumes to fix a failed
    test. Named deployment state is needed to reopen an existing ledger.

A. COMPLETE MAIN-API ROUTE LIST

Roles: R = any provisioned role, W = official or fact_checker, O = official.
GET calls read state. POST calls can append ledger/off-chain records unless
rejected, or can return an existing result when repeated idempotently.
{id} means a real report ID; {msp} means an MSP ID such as Org1MSP.

    Method  Path                                      Role / expected behavior
    GET     /health                                   none / 200, status ok
    GET     /api/status                               R / 200, Fabric/IPFS status
    GET     /api/orgs                                 R / 200, registered orgs
    GET     /api/reports                              R / 200, paginated records
    POST    /api/reports                              W / 200, id/hash/claim CID
    GET     /api/reports/{id}/chain                   R / 200, ledger record
    GET     /api/reports/{id}                         R / 200, stored claim/votes
    POST    /api/reports/{id}/fact-check              W / 200, independent vote
    POST    /api/reports/{id}/finalize                O / 200 only if majority met
    POST    /api/reports/{id}/expire                  O / 200 only if eligible
    POST    /api/reports/{id}/corrections             W / 200, new linked report
    POST    /api/reports/{id}/interventions           W / 200, evidence commitment
    GET     /api/reports/{id}/interventions           R / 200, intervention list
    GET     /api/reports/{id}/history                 R / 200, committed history
    GET     /api/reports/{id}/verify                  R / 200, integrity results
    POST    /api/orgs/{msp}/admission                 O / 200, eligible candidate
    POST    /api/orgs/{msp}/admission/vote            O / 200, eligible member vote
    POST    /api/orgs/{msp}/admission/finalize        O / 200, admission decision
    GET     /api/orgs/{msp}/admission                 R / 200, existing application

Report-list query arguments:
    status=PENDING, UNDER_REVIEW, FINAL, DISPUTED, EXPIRED or SUPERSEDED;
    omit status to include all statuses. page_size is 1..200 (default 50).
    Pass the returned next_bookmark unchanged through URL query encoding to
    fetch another page. An empty next_bookmark means no further page.

Main POST payloads:
    /reports and /corrections:
      {"msg_id":"unique-id","label":"1","confidence":0.9,
       "model_version":"manual-api-test","content":"Synthetic test claim",
       "source_platform":"manual-test"}
      Optional: published_at, inference_timestamp, supersedes (strings).
      A correction references a current FINAL report. Give it a NEW msg_id.
    /fact-check:
      {"outcome":"1","reasoning":"Synthetic review only","support":[]}
    /interventions:
      {"intervention_id":"unique-id","action":"Record test notice",
       "outcome":"Synthetic notice recorded","support":[]}
    /admission:
      {"org_name":"Candidate organisation","org_type":"research"}
    /admission/vote:
      {"verdict":"1"}
    /finalize, /expire, /admission/finalize: no JSON body required.

Labels/outcomes/verdicts are the strings "0" or "1". The manual examples below
choose synthetic labels; they do not run the AI or demonstrate model accuracy.
Use feed/manual-API report IDs for content verification. Direct Caliper records
deliberately have no stored IPFS claim and cannot pass full content retrieval.

B. COPYABLE MAIN-API WORKFLOW AND REJECTION CHECKS

[ ] Run this ONE complete block. It prints each method/path/status and asserts
    expected results. It creates TWO synthetic reports, review evidence and one
    intervention. Repeating it creates new test records. Do this outside timed
    feed/Caliper runs. Expected 400/401/403/409/422 rejections are labelled.
    The script stops at the first unexpected response; it does not roll back
    successful earlier writes. Keep its output as functional evidence.

    Reviewers are selected from each report's frozen eligible_reviewers and
    required_votes. This works dynamically with the provisioned org count.

    export API_TEST_NAME=development

repair/.venv/bin/python - <<'PY'
import json, os, urllib.error, urllib.parse, urllib.request, uuid
from blockchain.scripts.deployment import runtime_path

runtime = runtime_path(os.environ.get('API_TEST_NAME', 'development'))
cfg = json.loads((runtime / 'experiment.json').read_text())
rows = json.loads((runtime / 'credentials.json').read_text())
keys = {(r['org'], r['role']): r['api_key'] for r in rows}
base = f'http://127.0.0.1:{cfg["port_base"]}'
print('Deployment:', cfg['name'], '| organisations:', cfg['orgs'], '|', base)

def api(method, path, body=None, org='org1', role='fact_checker',
        expected=200, auth=True, bad_key=False):
    headers = {'Content-Type': 'application/json'}
    if auth:
        headers['X-API-Key'] = 'invalid-test-key' if bad_key else keys[(org, role)]
    request = urllib.request.Request(base + path, method=method, headers=headers,
        data=None if body is None else json.dumps(body).encode())
    try:
        with urllib.request.urlopen(request, timeout=180) as response:
            status, raw = response.status, response.read()
    except urllib.error.HTTPError as error:
        status, raw = error.code, error.read()
    result = json.loads(raw) if raw else None
    print(method, path, '->', status, '(expected', str(expected) + ')')
    if status != expected:
        print(json.dumps(result, indent=2))
        raise AssertionError('Unexpected API response; inspect this stage')
    return result

def chain(report_id):
    return api('GET', f'/api/reports/{report_id}/chain')

def majority(report_id, outcome):
    record = chain(report_id)
    required = record['required_votes']
    assert required == len(record['eligible_reviewers']) // 2 + 1

C. CONDITIONAL ADMISSION / EXPIRY CALLS

These routes are listed for completeness. A normal startup registers ALL its
provisioned organisations as founders, so it has no unregistered candidate for
a successful admission test. Admission also does not create peers/certificates.
Only test a successful admission after explicitly configuring an authenticated
candidate MSP which is not yet registered on the ledger.

In a Python session with the api() helper from B, the sequence would be:

    api('POST', '/api/orgs/Org4MSP/admission',
        {'org_name': 'Candidate organisation', 'org_type': 'research'},
        org='org4', role='official')
    api('GET', '/api/orgs/Org4MSP/admission', role='observer')
    api('POST', '/api/orgs/Org4MSP/admission/vote',
        {'verdict': '1'}, org='org1', role='official')
    # Repeat the vote with the required other eligible member identities.
    api('POST', '/api/orgs/Org4MSP/admission/finalize', role='official')
    api('GET', '/api/orgs', role='observer')

Org4MSP is only an EXAMPLE; the default three-org deployment has no org4 key.
The helper in B exists inside that Python block only: put conditional calls
inside a new copy of the block after its helper definitions, not in Bash.
Inspect the admission record and actual consortium policy before finalizing;
membership admission uses its own two-thirds threshold, separate from the
strict majority of frozen independent reviewers used for report verdicts.
Expected rejections: fact_checker/observer admission writes -> 403; request for
a different MSP from the authenticated candidate -> 403; registered founder
request -> 400; vote {"verdict":"admit"} -> 422. Missing applications produce
contract errors (normally 400), rather than a guaranteed HTTP 404.

Expiry call with the same helper:

    api('POST', f'/api/reports/{overdue_report_id}/expire', role='official')
    assert chain(overdue_report_id)['status'] == 'EXPIRED'

Use an actual unresolved PENDING/UNDER_REVIEW report past fact_check_deadline
(normally 72 hours). A fresh report correctly returns 400, as checked in B.
The background expiry task may already have expired it; repeating that expiry
is idempotent. Do not change system time or edit the ledger to force this test.
For a controlled positive expiry test use the existing automated tests or the
separate disposable retention check in section 11.

F. INTERNAL / OPTIONAL API INVENTORY

These are not additional public ports to open for normal testing. Current
storage/signers are private Docker-network services. Do not use an unrelated
old container at localhost:9100/9101 as evidence about this named deployment.

Internal storage bridge (port 9101 INSIDE its Docker network):
    GET  /health                 -> IPFS availability/version, no key needed
    POST /add                    -> raw request-body bytes; returns {"cid":...}
    GET  /cat/{cid}              -> exact stored bytes, not necessarily JSON
    POST /admin/unpin/{cid}      -> removes pin; disposable retention tests only
    POST /admin/gc               -> collects unpinned content; same restriction
    All except /health require X-Service-Key. Expected invalid/missing key: 401.
    /add empty body -> 400; object over 4 MiB -> 413.
    Use section 11 to test content removal on disposable state. Do not unpin
    evidence or run garbage collection on your demo/poster ledger.

Internal organisation signer (port 9100 INSIDE its Docker network):
    GET  /health                 -> organisation/schema status
    POST /query                  -> {"function":"QueryReport","args":["ID"]}
    POST /invoke                 -> {"function":"FinalizeReport","args":["ID"]}
    Both POST routes require X-API-Key and enforce their function/role allowlist.
    The signer owns one organisation's identities. Supplying an org selector
    in the body is rejected (400); invalid key -> 401; forbidden action -> 403.
    Public /chain and workflow calls exercise these signer paths normally.

Optional fact-checking-service compatibility wrapper:
    GET  /health
    GET  /claims/pending
    GET  /claims/{id}
    POST /claims/{id}/fact-check  -> {"outcome":"1","reasoning":"Test","support":[]}
    POST /claims/{id}/finalize   -> no body; official credential still needed
    /claims routes require X-API-Key from its configured organisation key map.
    This wrapper is not started by the current startup/feed path. Its presence
    in the source does not mean an additional service should already be running.

HTTP STATUS / RESULT INTERPRETATION
    200: request handled; ALSO inspect status/verified/availability in its body.
    400: workflow/ledger precondition rejected (e.g. self-vote, no majority).
    401: missing, invalid or revoked main API credential.
    403: authenticated role/organisation not permitted for this operation.
    404: unknown HTTP route; missing ledger entities can instead return 400.
    409: conflicting message ID/content or an integrity/commit conflict.
    422: request schema/value rejected (missing fields, invalid labels, etc.).
    503/504: service unavailable/deadline; inspect logs, not a functional pass.
    Connection refused: no listener on that address/port; check service lifetime.

Integrity verified=true means stored objects/history match their commitments.
It does not establish that the synthetic claim or a reviewer's verdict is true.
