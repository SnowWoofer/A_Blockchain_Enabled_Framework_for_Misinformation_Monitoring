FULL SYSTEM TEST CHECKLIST
==========================
For the notes-v1 Fabric deployment, full feed pipeline and official Caliper.
These examples target a fresh TLS development deployment (port 18000).
Older saved deployments require the deliberate reset described in README.md.
This checklist describes checks to run; it is not a claim every check has passed.
For another deployment, replace its name and read its saved port_base.
Older deployments retain the previous contract and cannot be upgraded by restart.
Keep their data, or deliberately reset test state using README.md.
See info/ArtyIndo/TONIGHT.md for the verification and overnight commands.
Updated: 19 October 2026 (notes workflow and transport TLS). Run commands from the project root in Linux/WSL.

This is a checklist to run manually, not a shell script. Tick each [ ] after
checking its expected result. Creating this file does not execute these tests.

WHAT COUNTS AS A NORMAL FUNCTIONAL PASS?
  Complete sections 1-8 for your selected deployment. Section 9 covers additional
  configurations; section 10 is optional AI evaluation; section 11 deliberately
  changes synthetic content/credentials in a separate disposable deployment.
  Section 12 is the evidence/reproducibility checklist; section 13 covers APIs.

Before starting:
  - Use one benchmark at a time. Stop Explorer during timed measurements.
  - A successful command normally exits with code 0. Run echo $? immediately
    afterward if unsure. A benchmark failure must be inspected in its logs.
  - Startup's smoke check, feed tests and Caliper writes append test records.
    They are not read-only. Repeating them grows the ledger.
  - Use the current feed command: benchmarks/pipeline.py. The older command
    called benchmarks/feed_samples.py is a different, direct-service workflow.
  - Keep the required scripts if you are following this complete checklist.
    Some optional research/check tools were listed as removable for normal use.
  - Preserve runtime folders, credentials and Docker volumes when troubleshooting.
    The deliberate one-time OLD-deployment reset in section 2 is the exception.

6. LIVE LEDGER RECORDS AND STORED-EVIDENCE VERIFICATION
------------------------------------------------------

repair/.venv/bin/python - <<'PY'
import json
from pathlib import Path
from blockchain.scripts.deployment import runtime_path, http
from blockchain.scripts.transport import configure_client
name = 'development'  # Change this for another deployment.
runtime = runtime_path(name)
cfg = json.loads((runtime / 'experiment.json').read_text())
credentials = json.loads((runtime / 'credentials.json').read_text())
key = next(c['api_key'] for c in credentials
           if c['org'] == 'org1' and c['role'] == 'fact_checker')
base = configure_client(runtime, cfg)
assert http(base + '/api/status', key=key)['ledger_backend'] == 'fabric'
latest = max(Path(f'results/repair/{name}').glob('feed-*/result.json'),
             key=lambda p: p.stat().st_mtime)
run = json.loads(latest.read_text())
assert run['result'] == 'passed'
print('Checking:', latest)
for sample in run['traces']:
    url = base + '/api/reports/' + sample['report_id']
    record = http(url + '/chain', key=key)
    proof = http(url + '/verify', key=key)
    assert record['status'] == 'FINAL', record['id']
    assert proof['verified'] and proof['history_verified'], proof
    print(sample['report_id'][:12], record['status'], 'verified:', proof['verified'])
first = run['traces'][0]['report_id']
print('First report:', first)
for entry in http(base + '/api/reports/' + first + '/history', key=key):
    print(entry['timestamp'], entry['record']['status'], entry['tx_id'])
print('Live ledger/evidence checks passed')
PY

    Expected: every report is FINAL and verified; history shows committed

    evidence are stored in IPFS; hashes/CIDs and review state are on-chain.

WHEN SOMETHING FAILS
---------------------
1. Stop at the failed stage; retain its printed logs.txt and failure/result JSON.
2. Check the selected --name and its saved experiment.json first.
3. Inspect services/logs without resetting data:

    repair/.venv/bin/python blockchain/scripts/deployment.py status --name development
    repair/.venv/bin/python blockchain/scripts/deployment.py logs --name development --services api signer1 peer1 orderer
    repair/.venv/bin/python blockchain/scripts/deployment.py logs --name development --services kafka
    ./blockchain/explorer/manage.sh logs --name development

4. For feed errors, also inspect worker_log_directory from failure.json.
   The malformed messages intentionally created by a successful feed test belong
   in its dead-letter files; an unverified startup probe or real sample does not.
5. Fix the specific cause and rerun the affected check. Do not repeatedly run
   large campaigns while the small functional check is failing.
6. Outside the deliberate old-deployment reset in section 2, do not use
   docker system prune, down -v, credential deletion or runtime-folder
   deletion as routine troubleshooting steps.

13. API TEST CALLS (APPENDIX)
-----------------------------
Run these from the project root after ./startup.sh --name development.

The main API also provides interactive documentation and exact request schemas:

A. COMPLETE MAIN-API ROUTE LIST

Roles: R = any provisioned role, W = official or fact_checker, O = official.
GET calls read state. POST calls can append ledger/off-chain records unless
rejected, or can return an existing result when repeated idempotently.
{id} means a real report ID; {msp} means an MSP ID such as Org1MSP.

    Method  Path                                      Role / expected behavior
    GET     /health                                   none / 200, status ok
    GET     /api/status                               R / 200, Fabric/IPFS status
    GET     /api/orgs                                 R / 200, registered orgs
    GET     /api/reports                              R / 200, paginated records
    POST    /api/reports                              W / 200, id/hash/claim CID
    GET     /api/reports/{id}/chain                   R / 200, ledger record
    GET     /api/reports/{id}                         R / 200, stored claim/votes
    POST    /api/reports/{id}/fact-check              W / 200, independent vote
    POST    /api/reports/{id}/notes                   W / 200, submitter org only
    GET     /api/reports/{id}/notes                   R / 200, attributed notes
    GET     /api/reports/{id}/history                 R / 200, committed history
    GET     /api/reports/{id}/verify                  R / 200, integrity results
    POST    /api/orgs/{msp}/admission                 O / 200, eligible candidate
    POST    /api/orgs/{msp}/admission/vote            O / 200, eligible member vote

Internal organisation signer (port 9100 INSIDE its Docker network):
    GET  /health                 -> organisation/schema status
    POST /query                  -> {"function":"QueryReport","args":["ID"]}
    POST /invoke                 -> {"function":"RecordReportNote","args":["ID","NOTE_ID","CID","SHA256"]}
    Both POST routes require X-API-Key and enforce their function/role allowlist.
    The signer owns one organisation's identities. Supplying an org selector
    in the body is rejected (400); invalid key -> 401; forbidden action -> 403.
    RecordReportNote enforces report ownership in the contract. Internal
    ExpireReport remains official-only; FinalizeReport/RecordIntervention are
    no longer permitted. QueryInterventions remains for historical verification.
    Public /chain and workflow calls exercise these signer paths normally.

Optional fact-checking-service compatibility wrapper:
    GET  /health
    GET  /claims/pending
    GET  /claims/{id}
    POST /claims/{id}/fact-check  -> {"outcome":"1","reasoning":"Test","support":[]}
    /claims routes require X-API-Key from its configured organisation key map.
    This wrapper is not started by the current startup/feed path. Its presence
    in the source does not mean an additional service should already be running.

HTTP STATUS / RESULT INTERPRETATION
    200: request handled; ALSO inspect status/verified/availability in its body.
    400: workflow/ledger precondition rejected (e.g. self-vote, no majority).
    401: missing, invalid or revoked main API credential.
    403: authenticated role/organisation not permitted for this operation.
    404: unknown HTTP route; missing ledger entities can instead return 400.
    409: conflicting message ID/content or an integrity/commit conflict.
    422: request schema/value rejected (missing fields, invalid labels, etc.).
    503/504: service unavailable/deadline; inspect logs, not a functional pass.
    Connection refused: no listener on that address/port; check service lifetime.

Integrity verified=true means stored objects/history match their commitments.
It does not establish that the synthetic claim or a reviewer's verdict is true.
