Blockchain-Enabled Framework for Misinformation Monitoring

Service API Reference

Every HTTP endpoint across the seven services — what it does, what it expects, and where the behaviour is not what you would guess.

Authentication. Two services require an X-API-Key header, and both accept the same org-level keys written by bootstrap-keys.sh (key-org1, key-org2, …). There is no user or account layer: an organisation authenticates as itself, and which person inside it is calling is that organisation's own concern. Ports shown are host-side; inside kafka_net the Python services all listen on :8000.

claim-ingest-worker

:8003no auth

Test harness. Pushes claim texts onto claims.raw so the rest of the pipeline can be exercised end to end. A stand-in for real ingestion — not part of the framework's claims.

GET/health

Liveness.

Response
{"status": "ok"}
POST/ingest

Queue one or more claim texts onto claims.raw.

Request
{"claims": ["<claim text>", "..."]}
Response
{
  "queued": 2,
  "ingest_ids": ["test_data_4039de7f…", "test_data_1b335e2d…"]
}
  • Mints ingest_id per claim as <source_platform>_<uuid4> and emits {ingest_id, source_platform, content, ingest_timestamp}.
  • Ids are random, not derived from content — the same text twice gets two different ids, and nothing can recompute one.

flagging-engine

:8004no auth

The model. Its real work is over Kafka — consumes claims.raw, publishes claims.inferenced. These endpoints are for direct scoring and observability.

GET/health

Liveness, plus whether the model has finished loading.

POST/predict

Score one piece of text directly, bypassing Kafka.

Request
{"post_text": "<text>"}
Response
{
  "label": "misinformation",
  "label_binary": "1",
  "confidence": 0.999955,
  "misinformation_probability": 0.999955,
  "model_version": "afro-xlmr-large-76L-misinfo-v1"
}
  • label is the model's argmax and confidence is the probability of that class — always ≥ 0.5, so it can never contradict the label.
  • label_binary is the ledger's domain. Emitted here because only this service knows its model's class ordering.
  • Sort on misinformation_probability, not confidence. Confidence is near 1.0 for a confidently benign claim and a confidently harmful one alike; only the probability spans the full range.
GET/metrics

Prometheus exposition.

  • flagging_engine_requests_total, flagging_engine_misinformation_total, inference latency, queue wait, batch size.

submission-worker

:8001no auth

Consumes claims.inferenced and calls the gateway's POST /api/reports for each claim. No request API — a claim it cannot submit is appended to a local dead-letter file rather than dropped.

GET/health

Liveness.

GET/metrics

Prometheus exposition.

  • claims_registered_total, claims_registration_failed_total, and the timestamp of the last successful write.

blockchain_gateway

:8000X-API-Key

The ledger and IPFS API. Assembles claim documents, computes inference_hash, publishes to IPFS, invokes chaincode. The API key determines which org signs the transaction.

GET/api/status

Off-chain storage status — whether IPFS is reachable and which backend is live (ipfs, or sqlite when degraded).

POST/api/reports

Register a claim. Called by the submission-worker, once per claim.

Request
{
  "ingest_id": "test_data_4039de7f…",
  "label": "1",
  "confidence": 0.999955,
  "model_version": "afro-xlmr-large-76L-misinfo-v1",
  "content": "<claim text>",
  "source_platform": "test_data",
  "published_at": "2026-09-07T09:14:22Z",
  "inference_timestamp": "2026-09-07T09:14:23.184627+00:00"
}
Response
{"root_cid": "Qm…", "inference_hash": "18f09cb4…"}
  • Nests the flat fields into source and inference, hashes exactly those two subtrees, publishes to IPFS, anchors the CID.
  • root_cid is the v1 CID and becomes the ledger key. It never changes.
GET/api/reports

List every on-chain record.

  • Optional ?status=PENDING|UNDER_REVIEW|REOPENED|FINAL|EXPIRED, filtered client-side after fetching all records.
GET/api/reports/{root_cid}

The full off-chain document at whichever version the ledger points to.

  • root_cid, current_cid and previous_cid are added on read so callers can walk the version chain.
GET/api/reports/{root_cid}/chain

The on-chain record only.

  • inference_hash, current_cid, inference_label, confidence, status, round, required_panel, fact_checks[], reopens[], and final_label once settled.
POST/api/reports/{root_cid}/fact-check

Submit one fact-check. This is also how a claim gets finalised — there is no separate finalise call.

Request
{"outcome": "0" | "1", "reasoning": "<free text>", "support": ["<url>"]}
Response
// still open
{"ok": true, "current_cid": "Qm…", "status": "UNDER_REVIEW",
 "round": 0, "required_panel": 3, "checks_this_round": 2}

// settled in this same transaction
{"ok": true, "current_cid": "Qm…", "status": "FINAL", "final_label": "1"}
  • Publishes a new document version carrying the reasoning and links, then invokes chaincode with that version's CID.
  • The chaincode closes the claim itself once the round reaches its panel with a two-thirds supermajority.
Rejected when
  • the claim is not open
  • the org already checked in this round
  • outcome is not "0"/"1"
POST/api/reports/{root_cid}/reopen

Reopen a FINAL claim at a panel two larger. Any registered org may reopen. No body.

Response
{"ok": true, "status": "REOPENED", "round": 1, "required_panel": 5,
 "standing_label": "1", "deadline": "2026-09-10T…",
 "reopens": [{"org_msp": "Org4MSP", "round": 1, "at": "…", "tx_id": "…"}]}
  • standing_label is deliberately not cleared. Reopening raises a question without withdrawing the consortium's answer while that question is open.
Rejected when
  • the claim is not FINAL
  • this org has already reopened it
  • it has been reopened three times
  • the next panel would exceed the registered org count
POST/api/reports/{root_cid}/expire

Close out a claim past its fact-check deadline.

  • A PENDING/UNDER_REVIEW claim becomes EXPIRED.
  • A REOPENED claim returns to FINAL with its standing verdict reaffirmed — a challenge that cannot gather its panel fails, rather than leaving the claim in limbo.
GET/api/reports/{root_cid}/verify

Tamper-evidence check.

Response
{"root_cid": "Qm…", "off_chain_intact": true,
 "matches_on_chain": true, "verified": true, "explanation": "…"}
  • off_chain_intact recomputes the document's hash from its own contents; matches_on_chain compares that to the anchored value. Both must hold.
GET/api/reports/{root_cid}/history

Every transaction that ever wrote this claim's ledger key, via Fabric's GetHistoryForKey.

  • Sorted oldest first, so [0] is the submission.
  • Each entry carries tx_id, timestamp, is_delete, and the full record as it stood at that moment.
POST/api/orgs/apply

Issue an API key for a new org.

Request
{"org": "org6"}
POST/api/orgs/{msp}/admission

Open an admission request for a candidate MSP.

POST/api/orgs/{msp}/admission/vote

Vote on admission.

Request
{"verdict": "0" | "1"}
POST/api/orgs/{msp}/admission/finalize

Admit the candidate if roughly two-thirds of registered orgs voted yes.

  • Admission uses a scaling supermajority of the whole consortium, unlike fact-checking's fixed small panel: admitting a permanent member is a governance decision, not a per-claim verdict.
GET/api/orgs/{msp}/admission

The current admission request and its votes.

GET/api/orgs

Registered orgs and when each was registered.

fact-checking-service

:8002X-API-Key

The API a fact-checking organisation actually uses. A thin org-facing layer over the gateway that adds a work queue and joins on-chain records to their readable off-chain content.

GET/health

Liveness.

GET/claims/pending

The caller's work queue.

  • Claims still open (PENDING, UNDER_REVIEW, REOPENED) that this org has not checked in the current round.
  • The per-round filter matters: after a reopen, an org that checked in round 0 may and should check again, so filtering on the whole history would hide exactly the claims that most need re-examination.
  • No assignment, no locking. Orgs pick from the queue; the chaincode rejects a submission if the claim closed meanwhile. Closed claims leave the queue and everyone moves on.
  • Each claim is enriched with its off-chain content — a fact-checker cannot fact-check a hash.
GET/claims/{root_cid}

One claim: the on-chain record joined to its readable off-chain document.

POST/claims/{root_cid}/fact-check

Submit a finding.

Request
{"outcome": "0" | "1", "reasoning": "<required, non-empty>", "support": ["<url>"]}
  • Validates outcome at this boundary and returns a readable 400 rather than passing an invalid value to the chaincode.
  • Otherwise identical in effect to the gateway endpoint, including automatic finalisation.
POST/claims/{root_cid}/reopen

Reopen a finalised claim. Same semantics and guards as the gateway endpoint.

fabric_gateway

:9100no authinternal

Node sidecar wrapping the official @hyperledger/fabric-gateway SDK. Holds each org's signing identity and is the only component that talks to peers.

GET/health

Channel, chaincode name, target peer, and which org identities are loaded.

POST/invoke

Submit a transaction and wait for commit.

Request
{"org": "org1", "channel": "mychannel", "chaincode": "misinformation",
 "function": "SubmitFactCheck", "args": ["<root_cid>", "1", "<new_cid>"]}
Response
{"ok": true, "status": "SUCCESS", "tx_id": "…"}
  • Returns the transaction id, not the chaincode's return payload. A caller needing the resulting state must query for it — which is why the gateway re-reads a record after fact-checking.
POST/query

Evaluate a read-only transaction. Same body shape; returns the decoded result.

ipfs_gateway

:9101no authinternal

A deliberately generic IPFS bridge. It knows nothing about claims, reports or hashing.

GET/health

Whether the IPFS node is reachable, and its version.

POST/add

Stores the raw request body in IPFS and returns its CID. No interpretation of the bytes.

GET/cat/{cid}

Returns the raw bytes for a CID, exactly as stored.
