# Election misinformation monitoring prototype

Multilingual AI triage, organisation-attributed review and immutable evidence
commitments on Hyperledger Fabric. This is a single-host research prototype.

**Normal use has three commands:** initialise your chosen database/organisation
count, then run either the feed benchmark or the Caliper benchmark. Run the two
benchmarks sequentially.

## 1. Install once

Use Linux or WSL 2 with Docker Compose, Python 3.12 and Go. Fabric 2.5.16
`cryptogen`, `configtxgen` and `osnadmin` must be under
`blockchain/fabric-samples/bin/`, with Fabric configuration under
`blockchain/fabric-samples/config/`.

Supply the existing model weights and tokenizer/configuration files under
`apps/flagging-engine/model/`, and the synthetic test dataset at
`data/translated_masked_samples_test.json`. These inputs are not generated by startup.

```bash
python3 -m venv repair/.venv
repair/.venv/bin/pip install torch==2.6.0+cpu --index-url https://download.pytorch.org/whl/cpu
repair/.venv/bin/pip install -r blockchain/scripts/requirements.txt
docker build -t misinfo-gateway:latest apps/fabric_gateway
docker build -t misinfo-blockchain-gateway:latest apps/blockchain_gateway
docker build -t misinfo-ipfs-gateway:latest apps/ipfs_gateway
docker pull hyperledger/fabric-peer:2.5.16
docker pull hyperledger/fabric-orderer:2.5.16
docker pull ipfs/kubo:latest
docker pull couchdb:3.4.2
docker pull apache/kafka:3.9.1
```

Skip installation if this environment is already set up. Commands below explicitly
use the virtual environment; activation is optional. Caliper builds its pinned
Docker image on first use, including official Caliper 0.7.1 and Fabric Gateway.
Docker needs network access for that first build. Image IDs and source checksums
are saved with runs; mutable image tags alone do not identify an exact environment.

## 2. Initialise the deployment

From the repository root:

```bash
./startup.sh --database leveldb --orgs 3
```

Choose `leveldb` or `couchdb`, and an integer organisation count of at least 3.
There is no arbitrary upper limit of 20; CPU, memory, disk and Docker resources
limit the network you can actually run. Generating a configuration above 20 is
not evidence of measured performance at that size.

The default name is **`development`**. A name is a label you choose, not a fixed
list of options. Names use lowercase letters, digits and hyphens, start with a
letter and contain at most 40 characters. All normal commands use `development`
unless you supply another `--name`.

Startup provisions Fabric/IPFS/API services, then tests a claim, majority reviews,
a correction, an intervention and evidence verification. Wait for the final
`Ready. Stop this deployment with: ...` message. The API binds to
`http://127.0.0.1:18000` by default.

Reusing a name keeps that deployment's database, organisation count, keys and
volumes. Explicitly conflicting arguments are rejected. Restart it with
`./startup.sh`, or choose a fresh name to create different state:

```bash
./startup.sh --name couch-five --database couchdb --orgs 5
```

(Above is not needed) Stop the other deployment first if both would use the same ports. Advanced users
can select another port base with `blockchain/scripts/deployment.py up --port-base`.
The benchmarks read their endpoints and configuration from the named deployment.
The root Docker Compose file is not the normal startup entry point.

## 3. Benchmark 1: full feed workflow

Leave the deployment running, then run:

```bash
repair/.venv/bin/python benchmarks/pipeline.py --samples 100 --seed 100
```

This runs the actual ingestion → Kafka → CPU INT8 AI → API/IPFS → Fabric path,
then applies scripted majority reviews and verifies evidence. It is not a separate
HTTP-only load test. HTTP remains part of the application's normal integration.

- `--samples 6` uses the same balanced six examples as the earlier integration test.
- Other positive counts select exactly that many unique records with seed 100 by
  default. Reusing the same seed, count and unchanged dataset reproduces selection.
- `--samples 0` processes the entire supplied dataset.
- A count larger than the available dataset is rejected; it is not silently reduced.
- Dataset IDs are reused for some distinct statements, so each trace records both
  its original ID and a fingerprint of the complete selected row.
- Reviewers and required votes come from each report's frozen ledger policy.
  Matching votes must exceed half of the eligible organisations, excluding the
  submitter. No particular two reviewer organisations are hardcoded.

Kafka readiness, CPU model loading and sequential reviews take time. The terminal
shows stages and periodic sample counts. A successful run ends with **`Feed PASSED`**.
Startup, sample timings, verification timings and recovery probes are recorded
separately. Scripted votes follow synthetic labels; they do not measure human
review time or real-world truth.

The run also checks pre-start backlog delivery, invalid-message dead letters and
subsequent valid-message delivery outside the sample-performance measurements.
Each invocation records current Kafka end offsets and commits them for its own
fresh benchmark groups **before** publishing the startup probe. This prevents
older test messages from being replayed into every new measurement. The probe is
still queued before the workers start and must reach verified storage. Offsets
are saved in `kafka-start-offsets.json` and the result. Existing topics and
production consumer-group offsets are retained.
Host workers stop when the command exits; Kafka stays with the named deployment.

## 4. Benchmark 2: Caliper reads and writes

After the feed command finishes:

```bash
benchmarks/caliper/run-caliper.sh
```

This uses **official Hyperledger Caliper with its Fabric Gateway connector** on
the same deployment. It measures `QueryAllReports` reads and committed `Submit`
writes, excluding REST, IPFS, AI and reviewer-finalisation costs.

Default settings:

| Setting | Default |
|---|---|
| Attempts | 1,000 writes, then 1,000 reads, shared across all workers |
| Workers | 2, submitting through Org1's gateway |
| Pending transaction load | 100 across all workers; a target backlog, not fixed TPS |
| Read operation | Full world-state report scan, on either database |
| Order | Write attempts, wait for completion, then read attempts |

The fixed-load controller adjusts submission rate to maintain the chosen pending
load. It does not fix throughput at 25 or 50 TPS. `startTps=25` is only the
controller's initial rate. Runtime depends on throughput, worker setup, inter-round
waits and transaction drain; short runs include the controller's ramp-up.
No fixture reports are inserted. Caliper 0.7.1 normally rounds each worker's count
down. A thin custom controller uses Caliper's public message setter to distribute
the remainder, then delegates pacing to its unmodified built-in fixed-load
controller. Thus `--count 5 --workers 2` gives worker totals of 3 and 2 per operation.

Reports retain official Caliper throughput, send rate, failures and latency,
plus recorded per-transaction timings. Caliper can include failed completions
in its reported throughput; successful throughput is therefore identified
separately and is zero when every transaction fails. The results describe observed
throughput under the recorded settings; this command does not search for maximum
capacity. A run with rejected transactions or incorrect attempt counts saves
`completed_with_failures` results and
returns a nonzero exit code; inspect the per-round counts and retained reports.
Failed write acknowledgements alone do not prove those transactions never committed.

For a short functionality check rather than a poster capacity measurement:

```bash
benchmarks/caliper/run-caliper.sh --count 6 --workers 2 --load 2
```

For a larger run:

```bash
benchmarks/caliper/run-caliper.sh --count 1000 --workers 2 --load 100
```

| Argument | Meaning | Default |
|---|---|---|
| `--count N` | N total write attempts, followed by N total read attempts | `1000` |
| `--workers W` | Client processes sharing each operation's total | `2` |
| `--load L` | Target number of pending transactions across all workers | `100` |
| `--name NAME` | Existing deployment; database and organisation count come from it | `development` |
| `--verbose` | Also stream detailed logs to the terminal | Off |

Count, workers and load must be positive integers; workers must not exceed count,
and load must be at least workers. For a single transaction, use `--count 1 --workers 1`.
The old `--duration`, `--loads`, `--fixtures` and `--repeats` arguments are retired.
Keep settings and initial ledger sizes comparable across databases/org counts.
Each read scans **all** reports, rather than looking up one of the new writes.
The runner records the initial and final ledger sizes. The final count also
provides a post-run indication of the read-stage size, rather than a snapshot at
its start. Avoid external writes while the benchmark runs; late commits after a
failed acknowledgement can also change ledger size. Historical results remain intact.

Caliper mounts only Org1's official client MSP and the gateway peer's TLS CA,
not Fabric CA/admin keys. No host Node/npm installation is needed for this runner.

## 5. Inspect the ledger with Hyperledger Explorer

With the named Fabric deployment running:

```bash
./blockchain/explorer/manage.sh up
./blockchain/explorer/manage.sh credentials
```

Open **http://localhost:18080**, select network **development**, and use the login
shown by the credentials command. To inspect another deployment, add the same
`--name YOUR_LABEL` to both commands. Explorer generates its profile from that
deployment's actual organisation count and uses an Org1 observer identity.
An Explorer database and wallet are retained separately for each deployment;
its PostgreSQL database is an index for the viewer, independent of Fabric's
selected LevelDB/CouchDB state database. The default web port is the deployment's
port base plus 80; use `up --port 19080` to choose another local port.

In Explorer, choose `mychannel` and inspect Blocks or Transactions. Report IDs are
in your feed's `result.json`; the corresponding Fabric transaction IDs are in
`GET /api/reports/REPORT_ID/history`. Search those transaction IDs in Explorer and
inspect the `misinformation` chaincode write set. Claim text and evidence remain
in IPFS, with their hashes/CIDs recorded on-chain; `/verify` checks their integrity.
Initial indexing can take time, and Explorer also lists setup and Caliper transactions.

```bash
./blockchain/explorer/manage.sh status
./blockchain/explorer/manage.sh logs
./blockchain/explorer/manage.sh down
```

`down` stops only Explorer and retains its database and wallet. Stop Explorer
before collecting performance measurements to keep background work comparable.
Private profiles and generated login credentials live under
`blockchain/runtime/NAME/explorer/` (or the existing legacy runtime location).
The launcher defaults to `development`; it does not start the Fabric deployment.

## Names, logs and results

For a different deployment, pass the same label to either benchmark:

```bash
repair/.venv/bin/python benchmarks/pipeline.py --name couch-five --samples 100 --seed 100
benchmarks/caliper/run-caliper.sh --name couch-five
```

Terminal output is deliberately short. Each invocation prints its unique directory
under `results/repair/NAME/`. That directory contains **`logs.txt`** and structured
results. Feed success saves `result.json`; Caliper saves `result.json`, `report.html`,
transaction records and generated configuration. Operational failures retain
diagnostics and `failure.json`; completed rounds with failures retain `result.json`.
Existing runs are not overwritten. Use `--verbose` to also
stream detailed diagnostics. Only one feed/Caliper invocation can use a named
deployment at a time; unrelated workloads on the same laptop can still affect timing.

Feed worker logs and dead letters remain private under the deployment runtime.
Do not publish runtime directories, credentials or private keys. A Git commit
alone does not identify uncommitted changes; run manifests also record source hashes.

## Inspect and stop

```bash
repair/.venv/bin/python blockchain/scripts/deployment.py status
repair/.venv/bin/python blockchain/scripts/deployment.py logs --services api signer1
repair/.venv/bin/python blockchain/scripts/deployment.py logs --services kafka
repair/.venv/bin/python blockchain/scripts/deployment.py down
```

Add `--name YOUR_LABEL` for another deployment. `down` retains named Docker volumes
and private runtime state. It does not remove unrelated projects.

New private state lives in `blockchain/runtime/`. Older deployments retain their
`experiments/runtime/` locations and resolve by name automatically. Do not delete
that state unless intentionally retiring the old deployment. Fresh identities
cannot recover an old ledger's access simply by reusing its name.

If a stage fails, inspect the printed log path. Ctrl+C cancels the command; it is
not a virtual-environment error. Child workers are cleaned up; deployment data is
retained. Do not delete volumes as a first troubleshooting step.

## Research boundaries and supporting material

The current prototype uses a single Raft orderer with no orderer failover and a
fixed two-peer endorsement policy. Reviewer majority, peer endorsement and ordering
are separate. No majority or hash proves factual truth. Private IPFS does not
provide evidence encryption at rest. Independent institutional administration,
production security, public trust and legal compliance have not been established.
