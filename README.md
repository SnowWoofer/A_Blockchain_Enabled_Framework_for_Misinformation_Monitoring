# Election misinformation monitoring prototype

Multilingual AI triage, organisation-attributed review and immutable evidence
commitments on Hyperledger Fabric. This is a single-host research prototype.

**Normal use has three commands:** initialise your chosen database/organisation
count, then run either the feed benchmark or the Caliper benchmark. Run the two
benchmarks sequentially. For tonight’s functional checks and matched overnight
commands, see [the short run guide](info/ArtyIndo/TONIGHT.md).

## 1. Install once

Use Linux or WSL 2 with Docker Compose, Python 3.12 and Go. Fabric 2.5.16
`cryptogen`, `configtxgen` and `osnadmin` must be under
`blockchain/fabric-samples/bin/`, with Fabric configuration under
`blockchain/fabric-samples/config/`.

Supply the existing model weights and tokenizer/configuration files under
`apps/flagging-engine/model/`, and the synthetic test dataset at
`data/translated_masked_samples_test.json`. These inputs are not generated by startup.

```bash
python3 -m venv repair/.venv
repair/.venv/bin/pip install torch==2.6.0+cpu --index-url https://download.pytorch.org/whl/cpu
repair/.venv/bin/pip install -r blockchain/scripts/requirements.txt
docker build -t misinfo-gateway:latest apps/fabric_gateway
docker build -t misinfo-blockchain-gateway:latest apps/blockchain_gateway
docker build -t misinfo-ipfs-gateway:latest apps/ipfs_gateway
docker pull hyperledger/fabric-peer:2.5.16
docker pull hyperledger/fabric-orderer:2.5.16
docker pull ipfs/kubo:latest
docker pull couchdb:3.4.2
docker pull apache/kafka:3.9.1
```

Skip installation if this environment is already set up. Commands below explicitly
use the virtual environment; activation is optional. Caliper builds its pinned
Docker image on first use, including official Caliper 0.7.1 and Fabric Gateway.
Docker needs network access for that first build. Image IDs and source checksums
are saved with runs; mutable image tags alone do not identify an exact environment.

## Full functional test on fresh deployments

```bash
./test_all.sh
```

Every invocation generates a unique name and selects free local ports. It runs
regression, real Fabric/API/role checks, AI/Kafka feed and repeated delivery,
TLS, small Caliper rounds, Explorer, restart persistence, and retention/revocation
on a separate disposable network. It stops only its own containers and retains
runtime data and evidence. No previous deployment or checkpoint is reused.
Use `./test_all.sh --plan` to preview coverage; [test_all.txt](test_all.txt)
documents options, results and limits. Optional `--matrix --evaluate-model`
adds database/org configurations and FP32/INT8 subset evaluation.

## 2. Initialise the deployment

From the repository root:

```bash
./startup.sh --database leveldb --orgs 3
```

Choose `leveldb` or `couchdb`, and an integer organisation count of at least 3.
There is no arbitrary upper limit of 20; CPU, memory, disk and Docker resources
limit the network you can actually run. Generating a configuration above 20 is
not evidence of measured performance at that size.

The default name is **`development`**. A name is a label you choose, not a fixed
list of options. Names use lowercase letters, digits and hyphens, start with a
letter and contain at most 40 characters. All normal commands use `development`
unless you supply another `--name`.

**TLS and notes update:** older saved deployments use an older chaincode package
and cannot be upgraded by restarting. Their data is retained. To reuse your normal
`development` name, follow **Reset an old test deployment** below. You do not need
a special “freeze” deployment; after your checks, save the source to GitHub as usual.

Startup provisions Fabric/IPFS/API services, then tests a claim, majority reviews,
submitter-only notes, retry/permission checks and evidence verification. Wait for the final
`Ready. Stop this deployment with: ...` message. The API binds to
`https://127.0.0.1:18000` by default.

Reusing a name keeps that deployment's database, organisation count, keys and
volumes. Explicitly conflicting arguments are rejected. Restart it with
`./startup.sh`, or choose a fresh name to create different state:

```bash
./startup.sh --name couch-five --database couchdb --orgs 5
```

Stop the other deployment first if both would use the same ports. Advanced users
can select another port base with `blockchain/scripts/deployment.py up --port-base`.
The benchmarks read their endpoints and configuration from the named deployment.
The root Docker Compose file is not the normal startup entry point.

### Reset an old test deployment

Run this only when you intend to discard **development's test ledger, stored
objects and identities**. Source code and saved benchmark results remain. Do not
use this to troubleshoot a deployment whose history you need to keep.

```bash
(
  set -e
  # Stop this deployment's Explorer if it was configured:
  if [ -f blockchain/runtime/development/explorer/state.json ]; then
    ./blockchain/explorer/manage.sh down --name development
  fi
  # Remove only development's containers and persistent test volumes:
  docker compose -p misinfo-v3-development -f blockchain/runtime/development/compose.json down --volumes --remove-orphans
  # Remove its old generated configuration/identities after Compose succeeds:
  rm -rf -- blockchain/runtime/development
  # Provision the current contract and TLS profile:
  ./startup.sh --database leveldb --orgs 3
)
```

If `development` is stored under `experiments/runtime/`, use that path in both
commands instead. The block stops if a command fails. Never
remove a runtime directory before removing its Compose volumes: losing the
identities while retaining the ledger leaves mismatched state.

### Transport encryption and trust

Normal startup generates a private deployment CA and separate service keys.
The API, internal signers, evidence bridges and host feed-worker HTTP listeners
use HTTPS. Kafka broker/controller/client connections use TLS; Kafka clients must
present a certificate. Fabric peer/orderer and external chaincode connections use
TLS. Python/Node clients verify the certificate chain and hostname. Keys are not
committed; the transport CA private key stays on the host.

For a direct API check:

```bash
curl --cacert blockchain/runtime/development/transport/ca.crt https://127.0.0.1:18000/health
```

Use this same public CA with API clients. A browser needs to trust that CA to use
`https://127.0.0.1:18000/docs` without a certificate warning. Do not disable
certificate verification in benchmarks. Existing helper scripts load the selected
deployment's CA automatically. Certificate lifetimes: service certificates 180
days, CA 365 days; this prototype does not automate certificate rotation.

Local exceptions are explicit: Kubo's management HTTP API is bound to loopback
inside its IPFS container's shared namespace with the HTTPS bridge. CouchDB HTTP
is bound to loopback inside its peer's shared namespace. Those RPCs do not cross
a Docker bridge. IPFS swarm transfers use libp2p's secure transport. Explorer is
an optional **loopback HTTP viewer**, with a TLS Fabric connection; stop it during
measurements. This is not a claim that every local RPC uses TLS. The optional
fact-checking compatibility wrapper is not launched or tested by this profile.

TLS decrypts data at the receiving process. It does **not** encrypt subsequent
disk writes: IPFS content, Kafka logs and dead-letter payloads remain unencrypted.
The API SQLite index stores unencrypted metadata (also payloads in the optional
SQLite development mode). Fabric state/history and runtime private keys also
remain readable to someone with the required filesystem or volume access.
Application-level encryption at rest is not implemented; deployment operators
must provide encrypted host/volume storage if that protection is required.

The existing `credentials.py` tool revokes a provisioned API key at the API and
signer; this is different from withdrawing a report or revoking a Fabric
certificate through a channel MSP CRL. Report `/verify` checks evidence integrity,
not real-world truth. One Raft orderer remains a single point of ordering failure;
this is a documented single-host prototype limitation.


## 3. Benchmark 1: full feed workflow

Leave the deployment running, then run:

```bash
repair/.venv/bin/python benchmarks/pipeline.py --samples 100 --seed 100
```

This runs the actual ingestion → Kafka → CPU INT8 AI → API/IPFS → Fabric path,
then applies scripted majority reviews and verifies evidence. It is not a separate
HTTPS-only load test. HTTPS remains part of the application's normal integration.

- `--samples 6` uses the same balanced six examples as the earlier integration test.
- Other positive counts select exactly that many unique records with seed 100 by
  default. Reusing the same seed, count and unchanged dataset reproduces selection.
- `--samples 0` processes the entire supplied dataset.
- A count larger than the available dataset is rejected; it is not silently reduced.
- Dataset IDs are reused for some distinct statements, so each trace records both
  its original ID and a fingerprint of the complete selected row.
- Reviewers and required votes come from each report's frozen ledger policy.
  Matching votes must exceed half of the eligible organisations, excluding the
  submitter. No particular two reviewer organisations are hardcoded.

Kafka readiness, CPU model loading and sequential reviews take time. The terminal
shows stages and periodic sample counts. A successful run ends with **`Feed PASSED`**.
Startup, sample timings, verification timings and recovery probes are recorded
separately. Scripted votes follow synthetic labels; they do not measure human
review time or real-world truth.

To submit some samples as other provisioned organisations, use:

```bash
repair/.venv/bin/python benchmarks/pipeline.py --samples 100 --seed 100 --random 30 --rejection-percent 20
```

`--random 30` assigns exactly 30 of the 100 samples to randomly selected
organisations other than Org1; the remaining 70 use Org1. Zero (the default)
uses only Org1; 100 uses only other organisations. Any provisioned organisation
count is supported. Percentages round to whole samples, with halves rounded up.
Selection is seeded independently of dataset selection and review-label overturns.
Random choice does not guarantee every other organisation appears in a small run.

Every sample follows the same ingestion/Kafka/AI path with its original text.
The submission worker uses the assigned organisation's actual provisioned
credential from a private run-scoped routing file; Kafka messages cannot select
an organisation credential. Reports retain organisation attribution, and the
actual submitting organisation is excluded from the frozen reviewer list.
These are scripted organisation submissions, not evidence of human participation.

`submission-plan.json` records the chosen organisations without credentials.
Each trace records `submitted_by`, `proposed_label`, `final_label` and verification;
`summary.submissions_by_org` records actual committed sample counts per MSP.
The private routing file is under the runtime worker-log directory and must not
be published. It is only enabled by the benchmark when other organisations are
assigned. Ingestion's optional planned message IDs are disabled in normal use.
Backlog/invalid-message recovery probes continue using Org1 outside sample counts.
If a routed submission fails, its dead letter records `_submission_org`; retain
that submitting identity when replaying it.

To demonstrate the majority **overturning the AI proposal**, use:

```bash
repair/.venv/bin/python benchmarks/pipeline.py --samples 100 --seed 100 --rejection-percent 20
```

This scripts 20 of the 100 reports to receive majority votes opposite to their
actual AI labels. The remaining 80 receive votes matching their AI labels. Every
report and its attributed votes stay committed; both outcomes have status `FINAL`.
This is a controlled workflow demonstration, not a classifier accuracy result or
a failed-transaction benchmark. It does not change model predictions or input data.

- `--rejection-percent P` accepts 0 through 100, including decimals. Zero upholds
  every AI label; 100 overturns every AI label.
- Counts round to the nearest whole sample, with halves rounded up. For six samples,
  20% means one overturn (16.67% achieved); 50% means exactly three.
- The same sample count, seed and percentage reproduce the planned sample positions.
- **Omitting the argument preserves the existing dataset-label review behaviour.**
  Its actual AI-overturn percentage depends on the model's predictions.
- `review-plan.json` saves the plan; `result.json` records the requested/actual
  percentage and upheld/overturned totals. Each trace keeps the original proposal,
  final label and verification result. Dataset labels remain in the unchanged input
  dataset, linked by the saved source fingerprint. All successful verified
  workflows count as successes, including those overturning an AI label.
- Keep this setting identical across comparative feed runs. Label controlled
  simulation results separately from the default dataset-label runs.

The run also checks pre-start backlog delivery, invalid-message dead letters and
subsequent valid-message delivery outside the sample-performance measurements.
Each invocation records current Kafka end offsets and commits them for its own
fresh benchmark groups **before** publishing the startup probe. This prevents
older test messages from being replayed into every new measurement. The probe is
still queued before the workers start and must reach verified storage. Offsets
are saved in `kafka-start-offsets.json` and the result. Existing topics and
production consumer-group offsets are retained.
Host workers stop when the command exits; Kafka stays with the named deployment.

## 4. Benchmark 2: Caliper reads and writes

After the feed command finishes:

```bash
benchmarks/caliper/run-caliper.sh
```

This uses **official Hyperledger Caliper with its Fabric Gateway connector** on
the same deployment. It measures `QueryAllReports` reads and committed `Submit`
writes, excluding REST, IPFS, AI and reviewer-finalisation costs.

Default settings:

| Setting | Default |
|---|---|
| Attempts | 1,000 writes, then 1,000 reads, shared across all workers |
| Workers | 2, submitting through Org1's gateway |
| Pending transaction load | 100 across all workers; a target backlog, not fixed TPS |
| Read operation | Full world-state report scan, on either database |
| Order | Write attempts, wait for completion, then read attempts |

The fixed-load controller adjusts submission rate to maintain the chosen pending
load. It does not fix throughput at 25 or 50 TPS. `startTps=25` is only the
controller's initial rate. Runtime depends on throughput, worker setup, inter-round
waits and transaction drain; short runs include the controller's ramp-up.
No fixture reports are inserted. Caliper 0.7.1 normally rounds each worker's count
down. A thin custom controller uses Caliper's public message setter to distribute
the remainder, then delegates pacing to its unmodified built-in fixed-load
controller. Thus `--count 5 --workers 2` gives worker totals of 3 and 2 per operation.

Reports retain official Caliper throughput, send rate, failures and latency,
plus recorded per-transaction timings. Caliper can include failed completions
in its reported throughput; successful throughput is therefore identified
separately and is zero when every transaction fails. The results describe observed
throughput under the recorded settings; this command does not search for maximum
capacity. A run with rejected transactions or incorrect attempt counts saves
`completed_with_failures` results and
returns a nonzero exit code; inspect the per-round counts and retained reports.
Failed write acknowledgements alone do not prove those transactions never committed.

For a short functionality check rather than a poster capacity measurement:

```bash
benchmarks/caliper/run-caliper.sh --count 6 --workers 2 --load 2
```

For a larger run:

```bash
benchmarks/caliper/run-caliper.sh --count 1000 --workers 2 --load 100
```

| Argument | Meaning | Default |
|---|---|---|
| `--count N` | N total write attempts, followed by N total read attempts | `1000` |
| `--workers W` | Client processes sharing each operation's total | `2` |
| `--load L` | Target number of pending transactions across all workers | `100` |
| `--name NAME` | Existing deployment; database and organisation count come from it | `development` |
| `--verbose` | Also stream detailed logs to the terminal | Off |

Count, workers and load must be positive integers; workers must not exceed count,
and load must be at least workers. For a single transaction, use `--count 1 --workers 1`.
The old `--duration`, `--loads`, `--fixtures` and `--repeats` arguments are retired.
Keep settings and initial ledger sizes comparable across databases/org counts.
Each read scans **all** reports, rather than looking up one of the new writes.
The runner records the initial and final ledger sizes. The final count also
provides a post-run indication of the read-stage size, rather than a snapshot at
its start. Avoid external writes while the benchmark runs; late commits after a
failed acknowledgement can also change ledger size. Historical results remain intact.

Caliper mounts only Org1's fact-checker client MSP and the gateway peer's TLS CA,
not Fabric CA/admin keys. No host Node/npm installation is needed for this runner.

The TLS deployment profile follows [Fabric external chaincode TLS](https://hyperledger-fabric.readthedocs.io/en/latest/cc_service.html)
and the [Kafka 3.9 SSL configuration](https://kafka.apache.org/39/configuration/broker-configs/).


### Matched overnight database measurements

First finish the short feed/Caliper checks above. Stop Explorer and other named
test deployments before timing. The block below creates three independent repeats
per database, with three organisations, TLS and identical settings. Keep the
source/configuration fixed, the laptop plugged in, Windows sleep disabled for the
run, and the terminal open. It is a manual command block, not an automatic startup job.
Use **new names**: retained reports from an earlier attempt change full-scan cost.

```bash
repair/.venv/bin/python blockchain/scripts/deployment.py down --name development
(
  set -euo pipefail
  for repeat in 1 2 3; do
    for database in leveldb couchdb; do
      name="night-${database}-r${repeat}"
      ./startup.sh --name "$name" --database "$database" --orgs 3
      benchmarks/caliper/run-caliper.sh --name "$name" --count 1000 --workers 2 --load 100
      repair/.venv/bin/python benchmarks/pipeline.py --name "$name" --samples 100 --seed 100
      repair/.venv/bin/python blockchain/scripts/deployment.py down --name "$name"
    done
  done
)
```

Caliper runs before the feed so every repeat starts with the same startup-only
report count. A failed command stops the block and retains its logs/state for
inspection. Do not silently resume a partially written ledger as a fresh repeat.
Record the fixed LevelDB-then-CouchDB order, hardware/WSL allocation, initial
ledger counts and failures. Summarise all repeats with variation; these are
observed results under chosen settings, not a maximum-capacity search. For an
optional separate full-dataset demonstration, `--samples 0` currently processes
1,401 rows sequentially and can take hours. Do not combine plaintext historical
results with new TLS measurements.

## 5. Inspect the ledger with Hyperledger Explorer

With the named Fabric deployment running:

```bash
./blockchain/explorer/manage.sh up
./blockchain/explorer/manage.sh credentials
```

Open **http://localhost:18080**, select network **development**, and use the login
shown by the credentials command. To inspect another deployment, add the same
`--name YOUR_LABEL` to both commands. Explorer generates its profile from that
deployment's actual organisation count and uses an Org1 observer identity.
An Explorer database and wallet are retained separately for each deployment;
its PostgreSQL database is an index for the viewer, independent of Fabric's
selected LevelDB/CouchDB state database. The default web port is the deployment's
port base plus 80; use `up --port 19080` to choose another local port.

In Explorer, choose `mychannel` and inspect Blocks or Transactions. Report IDs are
in your feed's `result.json`; the corresponding Fabric transaction IDs are in
`GET /api/reports/REPORT_ID/history`. Search those transaction IDs in Explorer and
inspect the `misinformation` chaincode write set. Claim text and evidence remain
in IPFS, with their hashes/CIDs recorded on-chain; `/verify` checks their integrity.
Initial indexing can take time, and Explorer also lists setup and Caliper transactions.

```bash
./blockchain/explorer/manage.sh status
./blockchain/explorer/manage.sh logs
./blockchain/explorer/manage.sh down
```

`down` stops only Explorer and retains its database and wallet. Stop Explorer
before collecting performance measurements to keep background work comparable.
Private profiles and generated login credentials live under
`blockchain/runtime/NAME/explorer/` (or the existing legacy runtime location).
The launcher defaults to `development`; it does not start the Fabric deployment.

## Report API and notes

Open `/docs` on the selected API port. Protected calls take the provisioned
`X-API-Key` header; there is no public signup or role selection.

### Checkpoint 2 roles and public verdicts

The `governance-v1` workflow retains the three certificate roles:

| Role | Permissions |
| --- | --- |
| Official | Founding setup, organisation admission requests/voting/finalisation, background expiry, authenticated reads |
| Fact-checker | Claim submission, eligible independent reviews, notes on its organisation's reports, authenticated reads |
| Observer | Authenticated internal reads; no writes |

Officials cannot submit claims, cast report-review votes, or append report notes.
An admission vote is distinct from a report-review vote. Report majority rules,
one vote per eligible organisation, and frozen reviewer sets are unchanged.

Anonymous visitors need no credential for `GET /api/public/reports` or
`GET /api/public/reports/{id}`. The list supports `page_size` (1–200, default 50)
and `bookmark`. Only `FINAL` reports are published; absent and non-final detail
requests return 404. Responses contain report ID/status/final label, submitting
organisation, finalisation time, required votes, content hash, and reviewers'
organisation/outcome/timestamp/transaction ID/evidence hash. These are ledger
verdict metadata, not a claim text search or independent integrity verification.
Raw claim content, reasoning, notes, CIDs, histories and internal configuration
remain behind the existing authenticated endpoints. Hashes are commitments,
not encryption or a guarantee that metadata is anonymous.

The API queries Fabric using a provisioned, server-held observer identity from
`PUBLIC_OBSERVER_CREDENTIAL_FILE`; it never supplies that credential to visitors.
Missing or revoked credentials make public queries unavailable (503).
Anonymous reads do not open signer, storage or peer access.

Use a fresh deployment name for Checkpoint 2:

```bash
./startup.sh --name checkpoint2 --orgs 3 --database leveldb
curl --cacert blockchain/runtime/checkpoint2/transport/ca.crt https://127.0.0.1:18000/api/public/reports
```

Earlier saved deployments are refused by the new startup path because their
chaincode grants different permissions. Their runtime state and volumes are
retained. A restart does not upgrade their chaincode. Keep the Checkpoint 1
commit with its original deployment; use a separate checkout if both versions
must operate concurrently, since generated deployments mount application source.
The API remains bound to loopback by default: anonymous means no application
credential, not automatic publication to the internet.

The report lifecycle is **submit → independent votes → automatic outcome**.
The deciding majority vote sets `FINAL`; all eligible votes without a majority
set `DISPUTED`. Unresolved reports expire automatically after 72 hours. Public
report-finalise and expire routes are removed. The internal expiry task and
its existing official credential remain unchanged.

Use **POST `/api/reports/{id}/notes`** for a correction, clarification, or a
reported action/outcome:

```json
{"note_id":"clarification-001","text":"Description and reported outcome.","support":[]}
```

Only fact-checkers from the report's submitting organisation can append
notes, at any report status. **GET `/api/reports/{id}/notes`** is available to all
authenticated roles and returns attribution, ledger timestamp/transaction ID,
content and verification results. Notes are append-only; they do not change a
report, its votes or verdict. Matching retries return the same note; conflicting
ID reuse returns 409. **GET `/api/reports/{id}/verify`** checks note commitments
as well as claims, reviews and historical evidence.

New correction/supersession and intervention routes are removed; historical
records remain readable and verifiable. Report retrieval includes
`legacy_interventions` with their content and availability/integrity flags.
A note records what its author says;
it does not independently validate a clarification or intervention's success.
Separate submissions with the same text remain allowed. Same-organisation/message
ID retries remain idempotent. Organisation admission routes are unchanged,
including their separate manual admission finalisation.

See [test_all.txt](test_all.txt) for the fresh-run test guide. For a submission,
review, note and public-access walkthrough on a running deployment, run
`repair/.venv/bin/python -m benchmarks.api_check --name YOUR_NAME` or open its
`/docs` schemas. The walkthrough creates synthetic records. No raw note text is
stored on-chain.

## Research boundaries and supporting material

The current prototype uses a single Raft orderer with no orderer failover and a
fixed two-peer endorsement policy. Reviewer majority, peer endorsement and ordering
are separate. No majority or hash proves factual truth. Private IPFS does not
provide evidence encryption at rest. Independent institutional administration,
production security, public trust and legal compliance have not been established.

See the [implementation record](info/ArtyIndo/repair/IMPLEMENTATION.md),
[research boundaries](info/ArtyIndo/repair/RESEARCH.md),
[manual report edits](info/ArtyIndo/edits_to_make.md),
[poster walkthrough](info/ArtyIndo/repair/DEMO.md) and
[poster/figure exports](info/ArtyIndo/repair/deliverables/README.md).
AI training notebooks and additional seeds/LoRA claims need your teammate's
original provenance; these scripts do not retrain the model.
