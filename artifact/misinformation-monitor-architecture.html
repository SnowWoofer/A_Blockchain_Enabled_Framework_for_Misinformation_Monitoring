Technical design · research prototype

Misinformation Monitor architecture

A consortium of fact-checking organisations reviews claims flagged by an AI model. Each organisation casts one vote on a Hyperledger Fabric channel, and a claim is confirmed as misinformation only when two-thirds of members agree. Claim documents live in a private IPFS swarm, with their fingerprints anchored on-chain. This document describes the prototype's structure, its main request flows and its security model.

branch feature/secure-prototype chaincode misinformation v2.3 Hyperledger Fabric 2.5 23 Oct 2026

01Overview

The system has two layers that start independently. The blockchain layer (startup.sh) provisions the Fabric network, the chaincode, a three-node IPFS swarm and the three gateways. The application layer (docker compose up) runs the AI screening pipeline, the fact-checking service and the web client.

People reach the system through one HTTPS entry point serving three audiences:

  • The public portal: anyone can search published verdicts, read the reasoning, check that a record was not altered, and submit claims anonymously.
  • The fact-checker workspace: member organisations review their queue and vote.
  • The officials' console: officials handle governance and user administration.

04Data and integrity

The ledger stores only what consensus needs: a fingerprint of the claim, the AI's initial label and each organisation's vote. The readable claim, the fact-checkers' reasoning and evidence links live in an IPFS document. The ledger key is the document's original CID, and the fingerprint covers only the parts of the document that never change, so later versions with added reasoning still verify against the same anchor.

05Report lifecycle

The chaincode decides every transition. With N registered organisations, a report needs required = ⌈2N/3⌉ "misinformation" votes from the N − 1 organisations that did not submit it. A vote can open, confirm or close a report in the same transaction.

Consensus changes in chaincode v2.3

The submitting organisation may not vote on its own report. Early rejection now counts only eligible organisations as pending voters. Manual finalisation requires the window to have closed. The quorum formula is unchanged, and the benchmark harness never let submitters vote, so FINAL/REJECTED outcomes are unaffected; a REJECTED report may close up to one vote earlier.

07Security model

The chaincode is the trust anchor. The gateway adds individual accountability and defence in depth, and the edge limits what the internet can reach. Every write is checked twice: once by the gateway's role check, and once by chaincode ABAC on the identity the gateway signs with.

7.5 Controls by layer

Chaincode

  • ABAC on the certificate's role attribute
  • Submitter may not vote on its own report
  • One vote per organisation per report
  • Early decision counts only eligible voters
  • Majority finalisation only after the window
  • Full history via GetHistoryForKey

Gateway

  • Individual accounts, bcrypt, lockout, optional TOTP
  • 15-minute JWT, rotating refresh cookie, reuse detection
  • One-time passwords with forced change
  • Role check on every route, mirrored to Fabric identities
  • Hashed, role-scoped API keys
  • Strict schemas, http(s)-only evidence links, 256 KiB cap
  • Hash-chained audit log with a verify endpoint

Service to service

  • Shared token to both sidecars; sidecar refuses to start without it
  • Chaincode function allow-list; reads only through /query
  • Separate HMAC keys per Kafka hop
  • De-duplication by msg_id
  • Fact-checking service forwards the caller's credential

Edge and containers

  • TLS 1.2/1.3, modern ciphers, configurable HSTS
  • CSP script-src 'self', no inline code in the build
  • Rate limits: sign-in 10/min, tips 6/min, API 30/s
  • Client X-Real-IP overwritten, X-Forwarded-For cleared
  • Unprivileged nginx, read-only root, all capabilities dropped
  • Non-root Python services

7.8 Residual risks

  • Single-host custody. One gateway and sidecar hold every organisation's identities. A real consortium would run one gateway per organisation with keys in an HSM, and enrol each person as a Fabric identity.
  • Blind review is a workflow property. Members can still query the ledger directly; vote secrecy would need commit-reveal.
  • Internal traffic is authenticated, not encrypted. Kafka runs PLAINTEXT and the sidecars use HTTP on the Docker network. Production would add Kafka SASL/TLS and mutual TLS.
  • Per-process limiters and audit log. The audit log is tamper-evident, not tamper-proof. Anchoring its head hash on the ledger periodically would close that gap.
  • Benchmark mode keeps well-known keys (key-orgN, stress-key) so the research harnesses run unchanged. Use --secure for anything else.
  • The old swarm key is in git history and must be rotated. Explorer still uses default credentials (loopback only). The certificate is self-signed by default.

08Deployment modes

The whole system comes up with one command, python3 up.py, and goes away with one command, python3 down.py. up.py checks prerequisites, clears any previous deployment, downloads the Fabric binaries if needed, generates secrets, starts every layer in order and waits for each service's health check. down.py removes every container, volume, network, chaincode image and runtime file the system created. It leaves research results, datasets, model weights and Fabric binaries alone; --purge also deletes secrets and built images.
